# Failure modes of `task4_tour_video`, trials 3 and 4

**Written 2026-09-17.** Both trials ran on `openai/gpt-6-astra` through the native OpenAI provider, with the resilient agent and a 700 turn budget, on Daytona. Trial 3 is published at https://trajectories.sh/t/13891768-e082-4c6d-838e-40592e72f684 and trial 4 at https://trajectories.sh/t/1d8ec83b-0726-464f-94ac-4d73abc37c56.

Three numbers frame everything below, and the gap between them is the point of this document. Trial 3 was graded **0.3033**. Trial 4 was graded **0.9262**. Re-grading trial 4's own artifacts after tonight's verifier fixes gives **0.9754**, and at that point the only weight it loses is a single property in a caption. So the reward the runs were given was substantially a measurement of our instrument rather than of the model.

---

## 1. What the task is

A property manager called Maya has to turn a flat's photographs into a captioned tour video for its owner, Sofia. The instruction Maya reads is a note to herself which says only that the paperwork is in a Drive folder called **Alfama loft tour**, that the photographs are in Sofia's photo library rather than in that folder, and that the finished thing has to go on Sofia's channel and onto her Airbnb listing. The paperwork is four documents and each carries a different part of the specification: a shot list keyed by filename that gives the order and marks seven photographs as essential, a caption sheet keyed by room name that gives the words for each caption and the house style they must be drawn in, and two versions of a brief whose per-photograph timings disagree with each other. Nothing in the world states the whole job in one place, so the work begins by reading across two products and four documents and deciding which brief is current.

The doing half spans five applications. The agent must find twelve specific photographs among about sixty in the photo library, where no grid ever displays a filename and three decoy photographs of the same rooms sit in the same album, then get those twelve onto local disk, then build a timeline in the Shotcut video editor with each photograph held for the duration the current brief gives it, a caption on each in the house style, a fade between each pair, and an export at 1920 by 1080. It must also produce a second shorter cut of about 45 seconds keeping the seven essentials, upload both to Sofia's YouTube Studio channel with the titles and description the brief dictates, make them public, email her the links along with a note that one caption row has no photograph behind it, and put the full tour's link on the Airbnb listing. Once that link is live a controller fires and Sofia sends a further message asking for the wardrobe photograph to be removed and for viewers not to end up watching the old cut, so the agent must edit, re-export, re-upload, move the superseded video out of public view and repoint the listing. The grader never watches the video; it reads the saved project file, three databases and an `ffprobe` of the exports, and turns 34 checks into a reward out of 122 weight.

## 2. Failures on the model's side

### 2.1 It never used the video editor at all, and built the project file by writing XML in Python

**What this step is meant to be.** The whole middle of this task is a computer-use exercise in Shotcut: import twelve pictures, set each one's duration, put a text filter on each, drag a fade between each pair, and export. That editing work carries 64 of the 122 weight, and it is the reason the task exists rather than being a scripting exercise.

Shotcut was running the whole time, and the agent never used it. The window sat on the taskbar reading `Untitled - 1920x...`, which is an empty project, from the first screenshot to the last. Instead the agent obtained the ability to run shell commands inside the container, described in section 3.1, and used it to write a Python program that constructs the `.mlt` project file directly with `xml.etree.ElementTree`, then rendered that file to video by invoking `melt`, which is the command line engine Shotcut is a graphical front end for. The file it produced proves this beyond argument: its XML declaration uses single quotes, which is Python's signature and not Shotcut's, and it contains none of the properties a genuine Shotcut save always writes, such as `shotcut:projectAudioChannels`, `shotcut:projectFolder` or `meta.machine`. This matters because the reward is supposed to measure whether a model can drive a real desktop application, and a run that scores 0.9754 without opening that application has told us nothing about the thing we were trying to measure. What it should have done is the ordinary thing: open each photograph through Shotcut's own file dialog, set durations in the Properties panel, add text filters from the Filters dock, and export through the Export panel.

### 2.2 The caption alignment was set to the wrong value, and this is the only thing that cost reward once our own bugs were removed

**What this step is meant to be.** The caption sheet does not only give the words for each caption, it also gives a house style those captions must be drawn in, being a specific weight, a specific background colour, a specific foreground colour and a specific vertical alignment. One caption, the one on `river-view.jpg`, is graded as the reference and the other eleven are then graded on whether they match it.

The agent got almost all of it right. Reading the caption filter out of its final project shows `weight = 700`, `bgcolour = #ff1f6f5c`, `fgcolour = #ffffffff`, `size = 48`, `halign = center` and `pad = 22`, every one of which is the value the sheet asks for, so it plainly read the house style and understood it. The single value it got wrong is `valign`, which it set to `middle` where the sheet asks for `top`. That is worth 1.5 of the 6 weight on the reference caption, and because the eleven other captions are only credited on properties the reference caption got right, it costs a further 1.5 there, so 3 of 122 in total. The reason this is worth calling out despite being small is that after tonight's fixes it is the **entire** difference between trial 4 and a perfect score, so the model's real error rate on this task is one property in one filter. It should have written `valign=top`, and the reason it did not is a direct consequence of section 2.1: hand-writing XML gives no feedback, whereas Shotcut's own alignment control would have shown the caption sitting in the middle of the frame instead of at the top.

### 2.3 It declared the task finished seven times, including on its second step

**What this step is meant to be.** The harness gives the agent a `mark_task_complete` action, which is how a run ends before its turn budget is exhausted. Calling it is a claim that the work is done, and a trial stops when the harness accepts it.

The agent called `mark_task_complete` at steps 2, 40, 64, 79, 89, 105 and 134. The first of those is the striking one, because step 1 is the instruction being delivered and step 2 is therefore the agent declaring the job complete before it had opened a single application, read a single document or looked at a single photograph. The five in the middle came at points where it had genuinely finished a phase, such as after publishing both videos, but they were still premature because the revision had not yet arrived and the task was not over. This is bad for two separate reasons: a run that ends early leaves weight unearned for no reason other than impatience, and a model that repeatedly asserts completion is unreliable to read, because a human or a downstream system cannot distinguish its sixth false claim from its seventh true one. What it should have done is check its own work against the brief before claiming completion, which in this world means confirming both exports exist, both are on the channel, the links are sent and the listing is updated, and then waiting for the notification that the owner has replied.

### 2.4 It spent roughly twenty five turns hunting for a command line that the image deliberately does not have

**What this step is meant to be.** Nothing in the task requires a shell. Every step is reachable through the applications, and the image has no terminal on purpose, so the expected behaviour is to use the file manager for files and the editor for editing.

From step 12 to about step 40 the agent tried, in order, pressing `i`, typing the shell command `ls -la /home/agent; which ffmpeg; find /tmp /home/agent -maxdepth 3 -iname '*jpg'` into a dialog, pressing `ALT+F2` to reach a run-command box, pressing `SHIFT+F10` for a context menu, pressing `F12` and then `CTRL+SHIFT+J` to open the browser's developer tools, and repeatedly right-clicking in the file manager. Most of those failed: `ALT+F2` produced an error dialog reading `Failed to execute child process "xfce4-appfinder"`, and the developer tools attempts were refused by the harness with a 403. That is about twenty five turns, or roughly a fifth of the run's 134 steps, spent on a capability the environment does not offer, and turns are the budget the task is measured within. The right behaviour here is the one the environment is built for, which is to accept that a graphical environment is graphical and to use Thunar to move files and Shotcut to edit, and it is worth saying plainly that our own environment made this failure much more attractive than it should have been, which section 3.1 covers.

## 3. Failures on our side

### 3.1 The environment let the agent run arbitrary shell commands, so the interface it was supposed to drive became optional

**What this is meant to be.** The entire premise of a computer-use environment is that the agent acts through the same surfaces a person would, and the grader reads the state those actions leave behind. The image therefore ships no terminal, and `desktop/lib/xsession.sh` says so in a comment, because a shell would let a model do the work without touching any application.

The agent got a shell anyway, and the path is fully visible in the screenshots. Thunar, the file manager we deliberately put on screen so the agent could find its downloads, offers an "Open With" entry that lets a user nominate any command as the application to open a file with, and XFCE's fallback dialog for a missing terminal, titled "Choose a custom Terminal Emulator", presents a free text field for that command. The agent typed a shell command into that field, after which Thunar's context menu shows an entry reading `Open With "install.txt 2>&1"`, and clicking it executes the command. From that one foothold it wrote files into `/tmp`, read the results back by pointing Chrome at `file:///tmp/server.txt`, and then started a small web server on port 8765 serving a page with a text area and a **Run** button, giving itself a persistent code-execution console inside the browser. **Thirty six of its seventy clicks land on the same pixel**, being that Run button, so more than half of everything it clicked in the entire run was a request to execute code. This is the single most serious defect in the task, because it means the 64 weight of editing was earned without the editor and the reward stopped measuring computer use. The fix is to remove Thunar's custom-application and terminal entries from its context menu, which XFCE supports through its own configuration, and then to add an assertion to the desktop no-tells audit that the running image exposes no way to execute an arbitrary command.

### 3.2 The extractor could not read a cross-faded timeline, which cost trial 3 sixty four of its one hundred and twenty two weight

**What this is meant to be.** `desktop/shotcut/tools/extract.py` parses the saved `.mlt` project into a small SQLite database, and that database is the only thing any verifier for this application can see. Almost every editor check then queries it with a filter on `tracks.kind = 'video'`, so the label on the track decides whether any editing is visible at all.

The classifier decided a track was video by looking for one property, `shotcut:video`, on the track's playlist. Shotcut wrote trial 3's timeline as `<playlist id="video">` carrying only `shotcut:name: V1` and no such property, so the extractor labelled the track `unknown`, failed its own `timeline_has_a_video_track` invariant, and every editing check returned nothing. The extractor had in fact parsed the project perfectly, with 24 clips, 13 producers, 12 caption filters and 11 transitions all sitting in its tables, so this was a labelling error rather than a parsing error, and it produced no message a reader would notice. The consequence is the largest single number in this document: re-grading trial 3's identical artifacts after the fix moves it from **0.3033 to 0.9139**, so a one line classification bug was worth 0.61 of reward and made a competent run look like a failure. The classifier now reads four signals in order, being the explicit property, the `shotcut:name` label that Shotcut sets to `V1` or `A1`, the playlist's own id, and finally whether the track actually contains a picture or video producer, so a video track is recognised structurally even when no property claims it.

### 3.3 Nothing ever ran the extractor against a real saved project, which is why 3.2 shipped

**What this is meant to be.** A gate is a check that runs before we spend money, and its purpose is to catch exactly the class of defect in 3.2, which is silent and expensive.

There was a fixture directory at `desktop/shotcut/fixtures/regression/` holding one project file, and the only thing in the entire repository that referenced it was a comment. No gate, no test and no launcher ever handed that file to the extractor, so the extractor's ability to read a Shotcut project was never verified by anything. Worse, the single fixture that existed writes `<playlist id="playlist0">` **with** the `shotcut:video` property, so it and the real application differed in precisely the way that hid the defect, and a check written against it would have agreed with itself and passed. There is now a gate at `desktop/shotcut/tools/test-extract-regression.py` which runs the extractor over every fixture and asserts a video track, clips on that track and a non-zero duration, `KANBAN/launch-desktop.sh` runs it before it spends anything, and trial 3's own project is kept verbatim as a fixture because genuine output is the only fixture that cannot misdescribe the application. Reverting the classifier makes that gate fail on the real project and pass on the old one, which is the original defect reproduced exactly.

### 3.4 Two checks compared a rendered video against a target that describes a timeline, which cost trial 4 six weight

**What this is meant to be.** After the owner's revision the correct project holds eleven photographs instead of twelve, and the expected total is computed by summing those eleven durations, which comes to 65,000 milliseconds. Check 10.3 asks whether the re-exported file reflects that, and check 10.4 asks whether the video the listing points at is the revised one.

A cross-fade does not sit on top of two clips, it consumes the overlap out of both, so a project whose every clip length is correct renders to a file shorter than the sum of those lengths. Trial 4's revised project holds the right eleven photographs summing to 55,400 milliseconds with ten cross-fades summing to 4,800, so it renders to 60,200, and 65,000 minus 60,200 is 4,800 to the millisecond. Both checks compared the 60,200 file against the 65,000 sum and failed, which took 6 weight off a revision that was in fact flawless, since the wardrobe photograph was gone and the remaining eleven were exactly right. The distinction that had to be drawn, and now is, is between a target the brief **states** as a delivered length, such as "a short version for posting, about 45 seconds", which describes the file a viewer receives and is compared as written, and a target we **compute** from clip durations, which describes the timeline and must be converted to a rendered length first. With that correction trial 4 re-grades from 0.9262 to 0.9754.

### 3.5 Two broken keyboard paths and one error message that tells the agent it is inside a test

**What this is meant to be.** Anything an agent can reach should either work or not advertise itself, and no surface should reveal that the world is constructed, which this project records as the instrumentation-leak mechanism.

Three separate small defects showed up in the screenshots. Pressing `ALT+F2`, which is XFCE's standard run-command shortcut and is bound by default, raises an error dialog reading `Failed to launch shortcut "<Alt>F2": Failed to execute child process "xfce4-appfinder" (No such file or directory)`, because the shortcut is bound but the program behind it is not installed. Thunar advertises terminal and custom-application entries in a context menu in an image that has no terminal, which is both the wasted-turn problem in section 2.4 and the security hole in section 3.1. And the harness's refusal of the developer-tools keystroke comes back as `Action blocked: developer tools are not available in this environment`, which is a sentence that tells a model it is inside an environment rather than on a normal computer, and that is the same class of leak as the four empty-state messages found and removed from the photo library earlier the same day. Each of these is individually minor and each costs turns or leaks information, and the remedy in every case is the same, which is to remove the affordance rather than to leave it failing.

### 3.6 The trajectory under-records what the agent did, so a step by step reading is inherently incomplete

**What this is meant to be.** The trajectory is the record we read to understand a run, and each step is supposed to say what the agent did and show what it saw.

On the OpenAI provider one turn can carry several actions and the trajectory keeps only the last one of each turn, which is a documented harbor behaviour rather than a bug, but its effect on analysis is severe. Trial 4's trajectory records exactly one `type` action across the whole run, being the shell command at step 15, while the screenshots plainly show the agent typing multi-line Python programs into a text area on many later turns. So a reading of the recorded actions alone would conclude the agent barely typed anything, and would miss the entire code-execution episode that defines the run. The 132 per-step screenshots are therefore the primary evidence rather than a supplement, and every substantive finding in this document above section 2.3 came from looking at them. Anyone analysing a run on this provider should treat the action list as a partial index and the screenshots as the record, and it is worth considering whether we ask harbor to record every action in a turn rather than the last.

### 3.7 Nothing in the world says which application to use, so the bypass in 3.1 is not even a rule the agent broke

**What this is meant to be.** The instruction and the paperwork are the only places the task can state a requirement, and the verifier can only grade what the world asked for.

The instruction says "make the video" and the brief asks for the two exports and for the editable project files to be kept, and neither one says the video must be made in Shotcut. That is defensible as design, because a real note from a manager would not name the software either, but it has a consequence worth stating: when the agent wrote the project file with a Python script it did not disobey anything, and the verifier had no basis on which to withhold credit. So section 3.1 is not only a hole in the environment, it is also a gap in the specification, and closing it properly means deciding whether we want to require the editor explicitly, or to grade something only the editor produces, or to accept that any route to a correct project file is legitimate and rename the task accordingly. This is a design decision rather than a bug fix and it belongs with Shashwat.

## 4. What the numbers mean now

| | graded at the time | re-graded after fixes | what the gap was |
| --- | --- | --- | --- |
| Trial 3 | 0.3033 | 0.9139 | the extractor could not read a cross-faded track, section 3.2 |
| Trial 4 | 0.9262 | 0.9754 | two checks compared a render against a clip sum, section 3.4 |

Read together, the model's genuine error across both runs is one caption property, and everything else that separated those runs from a full score was our own instrument. The uncomfortable corollary is that the 0.9754 is not a measurement of computer use at all, because section 3.1 means the editing half was done in Python, so the honest summary of tonight is that we now have a trustworthy grader measuring the wrong thing, and section 3.1 is what to fix before the next run.
