# Airbnb task repair log, 2026-09-05

This is the record of the repair pass over the six Airbnb task packages that followed scratchpad 55 (the failure inventory) and scratchpad 56 (the failure framework). It walks each task's mesh, instruction to initial state to application to agent to resulting state to oracle to grader, once for every known failure the inventory lists against that task and once for every failure class the framework predicts, and it records what changed, how the change was verified, and what is left. Every claim here about the current tree was checked by running the check named beside it on 2026-09-05; anything not run is marked as such in section 6.

Item numbers of the form 2C.7 refer to scratchpad 55. Framework classes are named as scratchpad 56 names them: the representation gap (meaning graded through a predicate that reads one rendering), the channel gap (a fact the world holds that no surface shows, or a control that cannot be operated), the replication gap (one fact kept in several copies that drift), the amplifiers (a grader that always returns a number, and gates that cascade so that one closed gate hides a third of a task), the composition of reactive systems (the controller and the Gmail persona reacting to the same email by different rules), and the process gap (a fix that exists in one tree and not in the package that runs).

## 2. Fixes that apply to every task

### 2.1 One clock, resolved from the world, advancing with real time (2D.1, 2D.2, 2D.3, 2D.4, 2H.3)

The controller no longer has a default clock and no longer trusts the environment variable. `resolveClock()` reads `environment_state.frozen_now` from the episode database on the first tick, and if `FROZEN_NOW` is also set and names a different instant it throws. `controllerNow()` returns that instant plus the real time elapsed since the controller started, and every write the controller makes uses it; the twelve literal `NOW` stamps that remained are gone. `eventStamp()` keeps its clamp above the newest thread, message and now notification, so an event still lands above a seed row stamped after the clock. The Airbnb clone writes with the same rule: `lib/clock.ts` gained `stamp()`, the pinned instant plus elapsed time, and the 28 write sites in 14 files that used the frozen constant now use it, while the two comparisons that test expiry (`request_expires_at`, session `expires_at`) keep the constant. The entrypoint refuses to start a scenario container without `FROZEN_NOW`, the Airbnb server line lost its 12:00 default, and the Gmail clone's `clock_offset_ms` is re-based at container start so that the mailbox's "now" is the task clock rather than the seeding machine's wall clock (the seed never wrote an offset at all; the mailbox ran on real time). The seed builder stamps every row it writes with the family's own clock instead of one constant, which is what made guest_trip_construction's listings sit three hours in the episode's future. The episode materializer's `FAMILIES` table is exported as `familyDefinition()`, host_ops_week reads 16:00 there as it does in the task materializer, and the task materializer throws if the two disagree.

Mesh walk. Forward: task.toml, the Dockerfile ENV line, episode.json and `environment_state` carry one value from one table; the entrypoint passes it to the app and the controller; the controller checks it against the database; the app stamps writes at clock plus elapsed; the controller stamps events at clock plus elapsed and above anything already there; the inbox orders by `updated_at`, so an injected ask sits at the top with its own preview; the verifier's contract does not read timestamps except through ordering by id. Backward from a graded ask that an agent never saw: it would have to sit below seed rows, which needs an event stamped at or below the seed, which needs either a clock behind the seed (audit checks 3 and 10 refuse the package) or a controller running on a different clock than the app (the cross-check throws). Verified: `node --test harbor/tests/*.test.mjs` (21 pass), `audit-task-integrity.mjs` (12 checks pass, including the four-copy clock equality), the Gmail offset snippet run against a copy of the games mailbox.

### 2.2 The Ops desk dictates a request format, and the world reads it two ways (2C.1, 2C.2, 2C.3, 2C.5, 2C.6, 2C.7, 2C.9, 2C.10, 2D.5, 2F.3)

The games Ops rules email now dictates the form of every request: `Action: BOOK | CANCEL | REVISE | RECAP`, `Listing:`, `Date: YYYY-MM-DD`, `Window: HH:MM-HH:MM`, `Extra: crib | extra bed`, one clean per email, and it says Ops answers every request on the agent's own thread so silence means nothing was scheduled. The controller exports the predicates that read a request: `opsRequestWhere` for the dictated form, matched after folding case and stripping whitespace so spacing cannot decide a grade; `opsProseWhere` for an ordinary sentence about the same clean, built from `dateMentionSql` (ISO, "September 2", "2 September", "Sept 2nd", "2nd of September", "02/09", plus task tokens such as "day 4", with digit boundaries so "September 2" does not match "September 20" or "September 2026") and `timeMentionSql` ("16:00", "4pm", "4 pm", "4:00 pm", "4 p.m.", "16h", guarded so "4pm" is not found inside "14pm"), and `approvalSql` for every ordinary way of asking a guest to accept a charge. An email written in the dictated form is judged by that form alone; the prose reading switches itself off when the body carries an `Action:` line, because a structured REVISE back to the original 11:00-13:00 window used to satisfy the prose reading of "moved to 13:00 or later" by mentioning 13:00. The contract builder imports these same functions, so the verifier grades exactly the predicate the world reacted to. Windows are graded by bounds parsed from the token (start at or after the checkout, end at or before the check-in), not by literal minutes, and the "12:00" that nothing in the world dictated is gone.

The Gmail persona matcher (`clones/gmail/apps/google/server/ops/mail.ts`) accepts arrays of needles for subject and body, matches after the same folding, gained `bodyExcludes`, and gained `replyInThread`, under which a canned reply is delivered into the thread of the email that triggered it with a `Re:` subject; `message.send` passes its thread id into the trigger context and `mail.deliver` honours a requested thread. The games persona's Ops entries are keyed on the dictated tokens: the Stadium conflict on a BOOK for Stadium Loft on 2026-09-02, a "held" confirmation on the REVISE to 14:00-16:00, a rejection on any other Stadium REVISE, booked, cancelled and rebooked confirmations for Marina View (the rebook chained after the cancellation), confirmations for the crib, the extra bed, the Riverside revision and the recap, and one bounce that answers the first email to Ops carrying no `Action:` line by restating the format. The chained "final" reply that used to fire on any second Stadium email is gone. A new seeded email from Ops lists the morning's schedule (Riverside Garden, 2026-09-04, 11:00-13:00, and nothing on 2 September) so the graded Riverside REVISE has a referent.

Mesh walk, forward: instruction ("book the cleans I need with Ops in the way they ask for them") to the rules email to the schedule email; the agent writes a BOOK in the form; `firePendingMail` folds the body, matches the entry, delivers Ops' answer into the same thread; the controller's next tick reads the same body with `opsRequestWhere`, cancels Amir's stay and writes his message above everything in the inbox; the contract's `marina_clean_initial` reads the same body with the same function inside `gmailOpsWhere`. Backward from a failed assertion: either the body lacks the tokens, in which case the persona also did not answer and the format bounce told the agent why, or the body is prose, in which case the prose reading applies, and the same prose reading gated the world. The two reactive systems now share one reading of an email. Verified: 47 positive and negative probe strings against the exported predicates (all pass), the controller test (recap not read as a booking; statement of intent not read as a booking; "Wednesday 2 September" prose read as a booking; "cancel" inside a recap does not summon the replacement request; a refusal to order the bed does not trip the trap; Ops replies in the agent's thread), and audit check 12 (below).

## 5. Decisions made in this pass that change a task

- The Ops desk dictates a request format, and both the world and the contract read a request in that format only (decided on 2026-09-06, TASK_FAILURES_DESIGN_DECISIONS.md item 2; the pass first shipped a prose fallback beside it). An agent that writes prose is answered, every time, with the format, and nothing is scheduled or credited until it uses it. Guest conversations on Airbnb have no dictated format and stay tolerant of every spelling of a date, a time or an agreement.
- Windows are graded by bounds, not minutes. Any clean that starts after the 11:00 checkout and ends by the 15:00 check-in is correct.
- The Marina View clean is booked against the arriving stay, and the rules say to cancel it when that stay cancels even though the flat still needs a clean. This is what makes the cancel step unambiguous.
- In negotiated_replan the alternatives that would have beaten the graded plan on price are off sale, and Marina View is Games-locked once cancelled. The exact multiset the contract grades is the only plan the instruction's own preferences lead to.
- In guest_trip_construction a corrected rate is the rate paid, by written policy.
- The controller reads its clock from the episode and checks the environment against it, rather than the other way round.

## 8. The browser replay (item 6 of the design decisions), added 2026-09-06

`harbor/scripts/replay-through-browser.mjs` drives Chromium (Playwright, from the Gmail clone's dependencies) against a running task container through the same hostnames the agent sees, follows a per-task module under `harbor/replays/` click by click, waits on the controller's own flags where the reference solution depends on a world reaction, then collects the databases and controller liveness exactly as the package's collect hook does and runs `verify.py`. Anything short of 1.0 names the assertion. Replays exist for `games_week_day_2` and `host_ops_week`; the other four tasks are not yet scripted.

The first runs found three defects that no other check had. The reply-to-self fix in the Gmail clone (2F.1) was inverted: it inferred "my own message" from the recipient list and got it backwards, so a reply to the Ops desk was addressed to Maya herself; it now compares the sender with the account's own address. The mail client measured "today" and "ago" against the browser's wall clock, so a mailbox pinned to 2 September showed its own sent mail as "4 days ago"; a `meta.clock` read now supplies the suite clock to the client's date formatting. The verifier took the controller tick count from the database row, which is written every twenty ticks, in preference to the per-tick artifact, and refused a ten-second replay whose controller had ticked seventeen times against a row that still said one; it now takes the larger of the two. Two selector mistakes in the replay scripts themselves (a search box filled instead of the sign-in field, a conversation box filled before its page had loaded) were the scripts' faults and are recorded here only because each is a thing an agent could also do.
